# BIM-S MCP Server №3

Отдельный сервер сравнения сохранённых снимков MCP-1 (3D) и MCP-2 (документация). C# / .NET 10, ModelContextProtocol 2.2.0, stdio. Работает без Revit, bridge, LLM и сетевых запросов приложения. Соседние проекты не используются как зависимости и не изменяются.

## Сборка и запуск

```powershell
dotnet build D:\BIM-S-MCP-3\BIM-S_MCP-Server-3\BIM-S_MCP-Server-3.csproj
dotnet D:\BIM-S-MCP-3\BIM-S_MCP-Server-3\bin\Debug\net10.0\BIM-S_MCP-Server-3.dll
```

Вторую команду запускает MCP-клиент. Сервер ожидает сообщения JSON-RPC на stdin; stdout занят исключительно транспортом MCP. Не запускайте через `dotnet run` в конфигурации клиента: вывод сборки может мешать протоколу.

Параметры отдельного подключения в MCP-клиенте:

- command: `dotnet`
- args: `["D:\\BIM-S-MCP-3\\BIM-S_MCP-Server-3\\bin\\Debug\\net10.0\\BIM-S_MCP-Server-3.dll"]`
- working directory: `D:\BIM-S-MCP-3`

Конфигурации существующих серверов не менялись. Пример для клиента, использующего TOML, дан в [docs/mcp-connection.example.toml](docs/mcp-connection.example.toml); это образец, а не установленное подключение.

Выходной каталог фиксирован: `D:\BIM-S-MCP-3_Отчеты_Версии модели`. Пользователю процесса нужны права записи в него. Входы читаются по абсолютным путям; они не переименовываются и не редактируются.

## Инструменты

### `compare-model-versions`

Проверяет запрос и полные снимки, сравнивает их, сохраняет JSON, затем HTML. Режимы `3d`, `2d`, `both`. Аргументы обёрнуты в объект `request`:

```json
{
  "request": {
    "mode": "both",
    "modelKey": "ПроектА",
    "oldVersion": {
      "versionId": "V001",
      "label": "Первая версия",
      "json3dPath": "D:\\BIM-S-MCP-1_Отчеты_Версии модели\\OLD_3D.json",
      "json2dPath": "D:\\BIM-S-MCP-2_Отчеты_Версии модели\\OLD_2D.json"
    },
    "newVersion": {
      "versionId": "V002",
      "label": "Вторая версия",
      "json3dPath": "D:\\BIM-S-MCP-1_Отчеты_Версии модели\\NEW_3D.json",
      "json2dPath": "D:\\BIM-S-MCP-2_Отчеты_Версии модели\\NEW_2D.json"
    },
    "pairing": {
      "confirmed": true,
      "method": "Пользователь указал пару файлов каждой версии одной модели",
      "scope3dDescription": "Один и тот же контрольный вид, одинаковые настройки видимости и отбора",
      "comparable3dScopeConfirmed": true
    }
  }
}
```

Имена `OLD_3D.json` и остальные — заглушки: замените точными путями. Не выставляйте подтверждения без знания происхождения снимков. В режиме `3d` можно опустить `json2dPath`, в режиме `2d` — `json3dPath` и оба поля области 3D. Всегда нужны `confirmed`, непустой `method`, `modelKey`, разные `versionId` и подписи.

Успешный `StructuredContent`: `status`, `comparisonId`, `mode`, `jsonPath`, `htmlPath`, `counts`, `limitations`. Ответ не содержит тяжёлых состояний элементов. Ошибка: `IsError=true`, `status=error`, `stage`, `message`, `jsonPath`. При ошибке HTML уже сохранённый JSON остаётся доступен. При невалидном снимке сравнение целиком прекращается: обычный успешный отчёт с непроверенными группами не создаётся.

### `create-model-comparison-report`

Аргумент `filePath` — абсолютный путь к JSON результата в каталоге отчётов MCP-3. Создаёт новый HTML, проверяя версию результата, группы, разности и счётчики. Исходные снимки не требуются. Существующий HTML не перезаписывается.

## Как подготовить версии

1. Выберите старую и новую версии **одной линии модели**. `modelKey` — ваша декларация, а не идентификатор, найденный сервером в Revit.
2. Для каждой версии создайте 3D и 2D последовательно, не меняя документ между выгрузками и во время них.
3. В MCP-1 используйте одинаковый контрольный активный вид и правила отбора. В MCP-2 — одинаковый `scope` и `includeTemplates`.
4. Запишите общую метку версии и точные пути двух файлов. Переименовывать JSON не требуется.
5. Передайте соответствие серверу явно. `old/new` определяются запросом, а не датами файлов.

Четыре изученных JSON MCP-1 от 27.09.2026 и два JSON MCP-2 от 28.09.2026 **не были автоматически объявлены двумя согласованными версиями**. Для них нужны сведения пользователя о соответствии. Встроенные проверки читают эти файлы и сравнивают каждый с самим собой.

## Политика `saved-state-v1`

Поддерживаются реальные схемы `schemaVersion=1`. Для MCP-2 дополнительно проверяется `contractVersion=1` и имя сервера. Сравниваются только полные выгрузки без необработанных ID и скрытых ошибок. `noValue`, `unsupported`, `notApplicable` сохраняют свой смысл. Для MCP-2 параметры должны охватывать все сущности графа. Отсутствующие массивы, дубли ключей JSON, сущностей, параметров и связей отклоняются. Явный пустой полный набор допустим.

3D: категория, семейство, тип, TypeId, параметры экземпляра и типа. 2D: объединение `sheets/views/placements/elements`, принадлежность к массиву, идентификаторы и описательные поля, все сохранённые `properties`, параметры и исходящие связи. Виды `View3D`, экспортированные MCP-2 как часть графа документации, остаются в разделе 2D.

Ключ элемента — положительный Int64 ElementId. Внутри 2D одинаковый ElementId с различающимися непустыми uniqueId вызывает ошибку идентичности. Имена и сходство параметров не служат ключом. Состояние типа учитывается у каждого содержащего его элемента. Типы не становятся отдельными элементами результата автоматически.

Параметры нормализуются в объекты по ключу `source:ownerElementId:parameterId`. Связи нормализуются по тройке `(kind, fromId, toId)` и относятся только к `fromId`; нет распространения изменений по графу. Порядок JSON-полей, элементов и параметров не влияет на сравнение. `builtInParameterNames` и `dependentViewIds` — множества; остальные массивы сохраняют порядок, включая геометрию и текстовые фрагменты.

Сравнение чисел точно нормализует десятичную запись без `double` и округления: `1`, `1.0`, `1e0` равны; большие Int64 и малые числовые различия сохраняются. Строки сравниваются точно. Отсутствующее поле отличается от `null`, пустой строки, нуля, false и пустого массива. Различия форматированных значений также являются изменением сохранённых данных. Служебные времена, сессии, snapshotId, пути и счётчики не входят в состояние элемента.

Все элементы раздела попадают ровно в одну из четырёх групп: `unchanged`, `changed`, `added`, `removed`. Проверяются оба баланса количества. Результат упорядочен по ElementId; поля и различия — по стабильным путям. Различие содержит JSON Pointer к нормализованному состоянию, `old/new` с `exists` и `value`. Изменение упорядоченного массива показывается как замена массива целиком.

## Формат результата и HTML

Корень JSON: `schemaVersion=1`, `policyVersion`, `comparisonId`, `createdAtUtc`, `request`, `limitations`, `sections`. Разделы `3d` и `2d` имеют `status=complete` или `notRequested`; у выполненных разделов есть `oldSource/newSource` (абсолютный путь, SHA-256 прочитанных байтов, метаданные), `counts` и четыре массива групп. Каждая запись содержит `elementId`, `oldState`, `newState`, `differences`. Отсутствующее состояние стороны — null. Для неизменившихся сохранены обе стороны; JSON самодостаточен для будущего внешнего анализа.

Имена: `comparison_<id>.json`, `comparison_<id>.html`. Пересозданный HTML имеет дополнительный уникальный суффикс. UTF-8, временная запись и переименование без перезаписи. Хеш рассчитывается по тем же байтам, которые сравниваются. JSON и HTML не являются одной атомарной транзакцией: при сбое второго этапа первый сохраняется.

HTML автономен, не требует JavaScript и сети. Стиль BIM-S: тёмная шапка, Segoe UI, белые карточки, таблицы и раскрываемые детали. Группы имеют светло-серый, бледно-жёлтый, бледно-зелёный и бледно-розовый заголовки. ElementId виден в каждой строке. Нет внешних ресурсов; все динамические значения HTML-кодируются. Полные исходные снимки дополнительно не встраиваются.

## Ограничения

- MCP-1 экспортирует выбранные элементы активного вида, но не сохраняет вид, идентификатор модели или uniqueId. `complete` не означает весь документ.
- `documentSession` относится к сеансу, а не версии. Название документа, GUID файла, snapshotId и близость времени не доказывают соответствие 3D/2D. Сервер сохраняет пользовательское подтверждение отдельно от доступных метаданных.
- Появление и удаление означают разницу состава снимков в заявленной области, а не доказательство создания/удаления во всём Revit-документе.
- Неизменность относится к сохранённым данным. Несохранённая геометрия и неподдерживаемые свойства не проверяются. Причины изменений не анализируются.
- JSON читается в память; результат хранит обе стороны состояний. Для крупных моделей потребуется достаточный объём памяти. Потоковая обработка не реализована.

## Проверки

```powershell
dotnet run --project D:\BIM-S-MCP-3\tests\Mcp3.Tests.csproj
```

Проверяет ядро, валидацию, HTML, сохранение, отмену, конфликт идентичности, точность чисел, реальные локальные снимки (только чтение, если каталоги доступны), MCP handshake и ошибки по stdio. Артефакты остаются в `artifacts/tests/<id>` внутри MCP-3.

Отдельная интеграционная проверка обоих инструментов с записью **синтетического демонстрационного отчёта** в рабочий каталог результатов:

```powershell
dotnet run --project D:\BIM-S-MCP-3\tests\Mcp3.Tests.csproj -- --production-smoke-only
```

Этот отчёт помечен `DEMO — синтетические данные, не версии Revit`; реальные файлы MCP-1/MCP-2 в пары не объединяются.

## Файлы проекта

- `SnapshotReader.cs` — два адаптера, полнота, типы, ключи и граф.
- `Canonical.cs` — точные числа, равенство и различия.
- `ComparisonEngine.cs` — подтверждения, совместимость, четыре группы.
- `Contracts.cs` — входные и выходные модели, JSON.
- `ReportFiles.cs` — запись в отдельный каталог.
- `ComparisonReport.cs` — проверка результата и автономный HTML.
- `ComparisonTools.cs`, `Program.cs` — MCP-инструменты и stdio.

Для будущего LLM-анализа используйте отдельного потребителя JSON результата. Ядро сравнения остаётся детерминированным и независимым от такого анализа.
